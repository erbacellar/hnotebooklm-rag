Fase I · Etapa 01

Pré-requisitos

Toda esta stack roda sobre Linux. No Windows, isso significa WSL2 — um Linux real rodando dentro do Windows, onde vivem o Hermes, o NotebookLM e o n8n. Esta etapa só garante que a base (sistema, Python, Node) esteja pronta antes de instalar as peças, pra você não travar no meio do caminho.

Você vai precisar de
  • WSL2 (Windows) com Ubuntu/Debian — ou Linux. Instalar o WSL2.
  • Python 3.10+, Node.js 18+ e git.
  • Conta Google (NotebookLM) e uma API key do Gemini (TTS de qualidade — Etapa 06).
  • Um bot do Telegram via @BotFather (guarde o token).

Verifique o básico

bash
python3 --version     # 3.10 ou maior
node --version        # 18 ou maior   (se faltar: sudo apt install nodejs npm)
git --version
ps -p 1 -o comm=      # deve imprimir: systemd
⚠ systemd no WSL2

Se a última linha NÃO imprimir systemd, habilite-o: edite /etc/wsl.conf (sudo nano /etc/wsl.conf), adicione as 2 linhas abaixo, salve (Ctrl+O, Enter, Ctrl+X) e no PowerShell rode wsl --shutdown e reabra o WSL.

/etc/wsl.conf
[boot]
systemd=true
Fase I · Etapa 02

Conceitos-chave

Antes de instalar qualquer coisa, vale entender as 4 peças do sistema e como elas dividem o trabalho — assim, em cada etapa seguinte, você sabe qual peça está mexendo e por quê. Pense nesta tabela como o "elenco" do projeto.

Em uma frase: o Hermes pensa e age, o NotebookLM lembra, o n8n automatiza, e o MCP é a ponte entre o Hermes e ferramentas externas como o n8n.

Fase I · Etapa 03

Instalar o Hermes — receita completa

O Hermes é o cérebro executor de todo o sistema: é ele que recebe suas mensagens, decide o que fazer, chama ferramentas (terminal, NotebookLM, n8n) e te responde. Ele sozinho não "pensa" — para isso, se conecta a um provedor de modelos (a inteligência que gera as respostas, como os modelos da Nous).

Nesta etapa você faz três coisas: instala o Hermes, faz login no provedor e valida que tudo responde. É a fundação — sem ela, nenhuma etapa seguinte funciona.

Antes
  • Python 3.10+ e pip (Etapa 01).

3.1 Instalar o pacote

bash
pip install hermes-agent
hermes postinstall      # instala dependências extras (Node, navegador, ripgrep, ffmpeg)

Se pip reclamar de ambiente gerenciado, use pipx install hermes-agent (instale antes com sudo apt install pipx).

3.2 Fazer login no provedor de modelos (Nous Portal — grátis)

bash
hermes setup --portal   # abre o navegador p/ login OAuth, define o Nous como provedor
                        # e ativa a Tool Gateway. Siga o fluxo no navegador.

3.3 Validar

bash
hermes status           # confira modelo, provider e o caminho do .env
hermes --tui            # abre um chat de teste (saia com /exit ou Ctrl+C)
# se algo estiver estranho:
hermes doctor           # diagnostica problemas comuns
hermes model            # reconfigura o provedor/modelo
⚠ Requisito do modelo

Escolha um modelo com ≥ 64K tokens de contexto. Há opções gratuitas no Nous Portal. Modelos grátis seguem instruções com menos fidelidade (relevante no roteamento e no diário, adiante) — os truques deste guia contornam isso.

📌 Disclaimer importante

As versões mudam com o tempo. Se qualquer comando aqui falhar ou divergir, o Quickstart oficial é sempre a fonte da verdade — consulte-o para se atualizar. Vale para todas as etapas deste guia.

Fase I · Etapa 04

NotebookLM (CLI) + a skill no Hermes

O NotebookLM (do Google) responde perguntas com base apenas nas fontes que você adiciona — links, PDFs, vídeos, textos — e cita de onde tirou cada afirmação. Diferente de um chat comum, ele não "chuta" do conhecimento geral: ele sintetiza o SEU material. É exatamente isso que o torna um bom "cérebro": você o alimenta com o que importa pra você, e ele vira uma memória pesquisável e confiável.

Você vai instalar duas coisas e é importante entender a diferença: a CLI notebooklm é o programa de linha de comando que controla o NotebookLM sem abrir o navegador; a skill é um "manual de instruções" que ensina o Hermes a usar essa CLI por intenção. Ou seja: a CLI dá o poder, e a skill ensina o agente quando e como usá-lo — assim, quando você pedir algo em linguagem natural no Telegram, o Hermes traduz sozinho para os comandos certos.

Antes
  • Hermes instalado · conta Google.

4.1 Instalar a CLI

bash
PYTHON=$(command -v python3.12 || command -v python3.11 || command -v python3.10)
$PYTHON -m venv ~/.notebooklm-venv
source ~/.notebooklm-venv/bin/activate
pip install "notebooklm-py[browser]"
playwright install chromium

# deixar o comando "notebooklm" acessível no PATH (sem sudo):
mkdir -p ~/bin
ln -sf ~/.notebooklm-venv/bin/notebooklm ~/bin/notebooklm
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc
notebooklm --version    # confirma que está acessível

4.2 Autenticar (login no Google via navegador)

bash
notebooklm login        # abre um Chromium; faça login na sua conta Google
notebooklm auth check   # valida (salva storage_state.json)
notebooklm list         # deve responder (vazio no começo)

4.3 Instalar a skill oficial no Hermes

bash
# 1. descubra a convenção de skills do SEU build:
hermes skills list

# 2. crie a pasta e grave a skill (gerada pela própria CLI):
mkdir -p ~/.hermes/skills/research/notebooklm
notebooklm skill show > ~/.hermes/skills/research/notebooklm/SKILL.md

# 3. confirme que o Hermes a enxergou:
hermes skills list | grep notebooklm
⚠ Armadilhas

• O caminho/formato de skill varia entre versões — confira com hermes skills list.
• Skills carregam no boot do gateway → após instalar/editar, reinicie o gateway (Etapa 08).

Fase I · Etapa 05

SOUL.md — a personalidade do agente

O SOUL.md é a alma do seu agente: um texto em prosa que define quem ele é, como fala e como se comporta. O Hermes lê esse arquivo a cada mensagem e "incorpora" o que está escrito — então é aqui que você molda o tom (direto? bem-humorado? formal?), as regras inegociáveis e até como ele interpreta suas intenções (por exemplo, decidir qual cérebro consultar).

Pense nele como o "briefing de personalidade" que você daria a um assistente humano no primeiro dia de trabalho. Quanto mais claro o briefing, mais o agente age do jeito que você espera — sem você precisar repetir instruções a cada conversa. É um arquivo vivo: você vai voltar aqui para refiná-lo nas Etapas 11 e 12.

Antes
  • Hermes instalado.

Fica em ~/.hermes/SOUL.md, é relido a cada mensagem (sem restart) e é prosa que o agente incorpora.

⚠ Maiúsculas importam

Linux distingue SOUL.md de soul.md — costuma ser maiúsculo. Confira: ls -la ~/.hermes/*.md.

Criar/escrever o arquivo

O bloco abaixo grava o arquivo inteiro de uma vez (cole tudo no terminal e dê Enter):

bash · grava ~/.hermes/SOUL.md
cat > ~/.hermes/SOUL.md <<'SOULEOF'
# Persona do Agente

<!-- Personalidade e tom. Carregado a cada mensagem. -->

Você é um assistente pessoal que vive no Telegram e ajuda no dia a dia:
estudos, organização, automações e memória.

## Como você fala
- Sempre em português do Brasil; inglês só quando necessário.
- Direto e didático; explique de forma que qualquer pessoa entenda.

## O que você nunca faz
- Nunca apaga arquivos sem perguntar.
- Nunca reexecuta um comando já executado sem confirmar.
- Nunca inventa: se não sabe, diz e consulta fontes confiáveis.

## Como acessar o cérebro (NotebookLM)
- Para perguntas de conhecimento, use a skill notebooklm DIRETAMENTE.
- Escolha o notebook cujo tema combina com a pergunta (use "notebooklm list").
- Nunca exija que o usuário diga o notebook ou a ferramenta.
SOULEOF
Dica

Antes de editar no futuro, faça backup: cp ~/.hermes/SOUL.md ~/.hermes/SOUL.md.bak.$(date +%s). Você vai somar diretrizes nas etapas 11 e 12.

Fase II · Etapa 06

Telegram, voz, foto e TTS natural

O Telegram é a porta de entrada do seu cérebro: em vez de abrir um terminal, você simplesmente conversa com um bot — de qualquer lugar, pelo celular. É o que transforma todo esse sistema técnico em algo que você usa no dia a dia sem fricção.

Aqui você conecta o bot ao Hermes e entende as três formas de entrada (texto, voz e foto), todas nativas. Um detalhe que faz muita diferença: o TTS (a voz que o agente usa para falar) — o padrão soa robótico, e a gente troca pelo Gemini para ficar natural.

Antes
  • Hermes instalado · token do bot (@BotFather).

6.1 Conectar o Telegram

bash
hermes gateway setup    # assistente: escolha "Telegram" e cole o token do bot;
                        # ele também pergunta seu ID de usuário autorizado.
hermes gateway run      # roda em foreground (a persistência vem na Etapa 08)

Mande qualquer mensagem ao seu bot — o Hermes deve responder.

6.2 Entradas (tudo nativo)

EntradaComo funciona
⌨️ TextoDireto.
🎤 VozSTT nativo: faster-whisper local (grátis, offline).
📷 Foto / OCRTool nativa vision_analyze → modelo multimodal.
📄 PDF/arquivoAnexe no chat; o agente adiciona como fonte.

6.3 TTS natural com Gemini — a dica que muda tudo

O TTS padrão soa robótico. Para voz natural, use o Gemini com sua API key (gere aqui). Passo a passo concreto de como gravar a chave no .env:

  1. Descubra o caminho do .env: hermes config env-path (ex.: /home/USUARIO/.hermes/.env).
  2. Abra no editor: nano ~/.hermes/.env
  3. Vá até o fim do arquivo e adicione uma linha (nome exato da variável na doc de Voice & TTS — em geral GEMINI_API_KEY): 
    ~/.hermes/.env (adicione no fim)
    GEMINI_API_KEY=cole_sua_chave_do_gemini_aqui
  4. Salve no nano: Ctrl+O → Enter (confirma o nome) → Ctrl+X (sai).
  5. Confirme e recarregue: hermes status (deve mostrar Google/Gemini ✓) e depois hermes gateway restart.

Fase II · Etapa 07

Usando o cérebro

Agora o cérebro ganha conteúdo. A ideia central é organizar o conhecimento em notebooks por tema (um para estudos, outro para trabalho, outro para notícias...). Cada notebook é um "balde" de fontes sobre um assunto — e essa separação é o que mais tarde permite o agente escolher o cérebro certo sozinho (Etapa 11).

O fluxo é sempre o mesmo: criar um notebook → adicionar fontes → perguntar (com citações) → opcionalmente gerar artefatos (podcast, infográfico). Quanto melhor a curadoria das fontes, melhores e mais confiáveis as respostas.

Antes
  • CLI notebooklm autenticada.

7.1 Crie notebooks por tema

PropósitoNome sugerido
EstudoBase de Conhecimento
TrabalhoProjetos
Feed de notíciasRadar Diário
Diário pessoalBordo
bash
notebooklm create "Base de Conhecimento"
notebooklm list      # anote o ID que aparecer

7.2 Adicione fontes

bash · troque ID_DO_NOTEBOOK
NB=ID_DO_NOTEBOOK
notebooklm source add "https://exemplo.com/artigo" -n $NB
notebooklm source add "https://youtube.com/watch?v=..." -n $NB     # transcreve
notebooklm source add --type text --title "Nota" -n $NB "texto inline"
notebooklm source add-research --mode deep "tema de estudo" -n $NB  # SEMEAR de uma vez

7.3 Pergunte e gere artefatos

bash
notebooklm ask -n $NB "Explique o tema e cite as fontes."
notebooklm ask -n $NB "..." --save-as-note
notebooklm generate audio -n $NB --format brief --length short
notebooklm language set pt_BR     # idioma GLOBAL dos artefatos
⚠ Lições

• Idioma é global: sem language set pt_BR, podcasts saem em inglês.
• Áudio é pesado (Telegram envia até ~50 MB) → converta: ffmpeg -y -i in.wav -ac 1 -b:a 64k out.mp3.
• add-research --mode deep só para semear — ruim para feed diário.
• O ask SINTETIZA; para texto literal use source list + source fulltext.

Fase II · Etapa 08

Persistência: o gateway que volta sozinho

Até aqui, o "gateway" (o processo que liga o Hermes ao Telegram) só roda enquanto o terminal está aberto — feche-o e o bot fica mudo. Esta etapa resolve isso transformando o Hermes num serviço de sistema (via systemd): ele passa a rodar em segundo plano, reinicia sozinho se travar e volta automaticamente quando a máquina liga.

É a diferença entre "um programa que eu preciso ligar toda vez" e "um assistente que está sempre lá". No WSL2 há um detalhe extra (o linger) que garante isso mesmo após você deslogar.

Antes
  • systemd habilitado (Etapa 01).
bash
hermes gateway install        # cria o serviço systemd de usuário
hermes gateway start
hermes gateway status         # deve mostrar: active (running)

# CRÍTICO no WSL: linger faz sobreviver ao logout e voltar no boot
sudo loginctl enable-linger $USER
loginctl show-user $USER | grep -i linger     # deve mostrar Linger=yes
⚠ Como recarregar depois

Mudou skill ou servidor MCP? Rode hermes gateway restart. (O SOUL.md NÃO precisa — é relido a cada mensagem.)

Teste o auto-boot

No PowerShell: wsl --shutdown, reabra o WSL e mande uma mensagem. Se responder sem você ligar nada, está ok.

Fase III · Etapa 09

n8n + MCP: dando braços ao cérebro

Até agora o cérebro pensa e lembra. Com o n8n ele ganha braços para agir: o n8n é uma plataforma de automação onde você monta "workflows" (sequências de passos que conectam apps e executam tarefas). Self-hosted, é gratuito e roda na sua máquina.

Para o Hermes conversar com o n8n usamos o MCP (Model Context Protocol) — um "idioma" padrão criado pela Anthropic em que o agente (cliente) pede e uma ferramenta (servidor) executa. Na prática: você cria uma ferramenta no n8n, ela vira um "servidor MCP", e o Hermes passa a chamá-la sozinho quando a intenção da sua mensagem combinar. É assim que, mais tarde, ele vai salvar/consultar seu diário ou disparar automações.

Antes
  • Node 18+ · Hermes como serviço.

9.1 Instalar (self-hosted, grátis)

⚠ EACCES no npm

Node via apt aponta o global para /usr/local (root). Não use sudo — redirecione para o seu home (o bloco abaixo já faz isso):

bash
mkdir -p ~/.npm-global
npm config set prefix "$HOME/.npm-global"
grep -q '.npm-global/bin' ~/.bashrc || echo 'export PATH="$HOME/.npm-global/bin:$PATH"' >> ~/.bashrc
export PATH="$HOME/.npm-global/bin:$PATH"
npm install -g n8n --loglevel=error
n8n --version

9.2 n8n como serviço systemd

bash · cria a unit e liga
cat > ~/.config/systemd/user/n8n.service <<'EOF'
[Unit]
Description=n8n workflow automation
After=network.target
[Service]
Type=simple
Environment=PATH=%h/.npm-global/bin:/usr/local/bin:/usr/bin:/bin
Environment=NODE_FUNCTION_ALLOW_BUILTIN=*
ExecStart=%h/.npm-global/bin/n8n start
Restart=on-failure
RestartSec=5
[Install]
WantedBy=default.target
EOF
systemctl --user daemon-reload
systemctl --user enable --now n8n
# abra http://localhost:5678 no navegador e crie a conta de dono (pule licença/trial)
⚠ NODE_FUNCTION_ALLOW_BUILTIN

Sem essa variável, o nó Code não consegue require('child_process') (necessário p/ chamar o notebooklm).

9.3 Expor o n8n como MCP e conectar o Hermes

  1. No n8n, crie um workflow com o nó MCP Server Trigger. Defina um Path (ex.: cerebro) e Bearer Auth com um token (gere com openssl rand -hex 24).
  2. Conecte ao trigger uma ferramenta (comece com uma Code Tool "olá mundo"). Salve e Ative o workflow.
  3. Registre no Hermes (responda os prompts; o valor do header é o token puro): 
    bash
    hermes mcp add n8n --url http://localhost:5678/mcp/cerebro --auth header
hermes mcp list
hermes mcp test n8n        # conecta e descobre as tools
  4. Habilite no config (nano ~/.hermes/config.yaml → em mcp_servers.n8n ponha enabled: true, salve com Ctrl+O/Enter/Ctrl+X) e rode hermes gateway restart.
⚠ Lições de ouro

• PATH em serviço systemd é mínimo: o nó Code roda via /bin/sh sem .bashrc → use caminho absoluto /home/USUARIO/bin/notebooklm.
• Heredoc no terminal quebra a indentação Python → crie scripts com base64 -d > arquivo.
• Tools são por plataforma: hermes tools --summary.

Fase III · Etapa 10

Construindo os Workflows do n8n

Nesta etapa você constrói os 4 workflows que formam o sistema de automação. Três são sub-workflows (executados por outro workflow, como funções reutilizáveis) e um é o servidor MCP (o ponto de entrada que o Hermes chama). A ordem importa: crie os sub-workflows primeiro, depois o servidor MCP que os usa.

Antes
  • n8n instalado e rodando em http://localhost:5678 (Etapa 09).
  • Gere um token Bearer: openssl rand -hex 24 e guarde.
flowchart TD MCP["🔌 Cerebro MCP"] -->|consulta_notebook_via_n8n| CC["Consulta Cerebro"] MCP -->|salvar_no_diario| SW["Salvar Diario"] MCP -->|consultar_diario| CC MCP -->|listar_diario| LW["Listar Diario"]

Workflow 1 — "Consulta Cerebro" (sub-workflow)

Recebe uma pergunta e o nome de um notebook, resolve o nome para o ID real e faz a consulta no NotebookLM. É reutilizado tanto pela ferramenta de consulta geral quanto pelo diário.

  1. Clique em + New Workflow e nomeie: Consulta Cerebro.
  2. Adicione o nó "When executed by Another Workflow" (Trigger). Dentro dele, defina dois campos de input:
    • Nome: pergunta  ·  Tipo: String
    • Nome: notebook  ·  Tipo: String
  3. Conecte um nó Code (JavaScript) à saída do trigger. Apague o código padrão e cole o código abaixo:
Nó Code — Consulta Cerebro
const { execSync } = require('child_process');
const NB = '/home/USUARIO/bin/notebooklm';  // substitua USUARIO pelo seu

let j = $input.first().json || {};
function pick(o,keys){if(!o)return null;for(const k of keys){if(o[k]!=null&&typeof o[k]!=='object')return o[k];}return null;}

let pergunta = pick(j,['pergunta','query','chatInput','input','question']);
let nb       = pick(j,['notebook','notebook_name','notebookName']);
if(!pergunta||!nb){
  for(const v of Object.values(j)){
    if(v&&typeof v==='object'){
      pergunta = pergunta||pick(v,['pergunta','query','chatInput','input','question']);
      nb       = nb||pick(v,['notebook','notebook_name','notebookName']);
    }
  }
}

pergunta = String(pergunta||'').replace(/"/g,'\\"');
const nbInput = String(nb||'').trim().toLowerCase();

// fallback: Estudos de IA — troque pelo ID do SEU notebook padrão
let nbId    = 'COLE_ID_DO_NOTEBOOK_PADRAO';
let nbTitle = 'Notebook padrão (fallback)';

if(nbInput){
  try{
    const out = execSync(`${NB} list --json`,{encoding:'utf8',timeout:60000});
    const nbs = JSON.parse(out.slice(out.indexOf('{'))).notebooks||[];
    const m   = nbs.find(n=>(n.title||'').toLowerCase()===nbInput)
             || nbs.find(n=>(n.title||'').toLowerCase().includes(nbInput));
    if(m){nbId=m.id;nbTitle=m.title;}
  }catch(e){}
}

let resposta;
try{
  resposta = execSync(`${NB} ask -n ${nbId} "${pergunta}"`,{encoding:'utf8',timeout:180000});
}catch(e){
  resposta = 'Erro: '+(e.stderr||e.message||String(e));
}

return [{ json:{ notebook_usado:nbTitle, resposta } }];
⚠ Atenção

Substitua USUARIO pelo seu usuário Linux (descubra com echo $USER) e COLE_ID_DO_NOTEBOOK_PADRAO pelo ID do notebook que deve ser o fallback (encontre com notebooklm list).

  1. Conecte o nó Code ao trigger arrastando o conector.
  2. Clique em Save (canto superior direito) e ative o workflow (toggle Active).

Workflow 2 — "Salvar Diario" (sub-workflow)

Recebe um texto e o salva como fonte no notebook do diário.

  1. Crie um novo workflow: Salvar Diario.
  2. Adicione "When executed by Another Workflow". Defina um campo:
    • Nome: texto  ·  Tipo: String
  3. Conecte um nó Code e cole:
Nó Code — Salvar Diario
const { execSync } = require('child_process');
const NB     = '/home/USUARIO/bin/notebooklm';   // substitua USUARIO
const DIARIO = 'COLE_ID_DO_NOTEBOOK_DIARIO';     // ID do notebook "Bordo"

let j     = $input.first().json || {};
function pick(o,keys){if(!o)return null;for(const k of keys){if(o[k]!=null&&typeof o[k]!=='object')return o[k];}return null;}
let texto = pick(j,['texto','text','conteudo','nota','content']);
if(!texto){for(const v of Object.values(j)){if(v&&typeof v==='object'){texto=texto||pick(v,['texto','text','conteudo','nota','content']);}}}

texto = String(texto||'').replace(/"/g,'\\"');

let out;
try{
  const result = execSync(`${NB} source add --type text -n ${DIARIO} "${texto}"`,{encoding:'utf8',timeout:120000});
  out = 'Anotação guardada no diário. '+result.trim();
}catch(e){
  out = 'Erro ao guardar: '+(e.stderr||e.message||String(e));
}
return [{ json:{ resultado:out } }];
  1. Substitua USUARIO e coloque o ID do notebook do diário (ex.: o "Bordo" criado na Etapa 07).
  2. Save + Active.

Workflow 3 — "Listar Diario" (sub-workflow)

Não recebe nenhum input — lista todas as entradas do diário com o texto literal.

  1. Crie: Listar Diario.
  2. Adicione "When executed by Another Workflow" e deixe sem campos (accept all data).
  3. Conecte um nó Code com o seguinte script (que foi instalado via base64 — aqui é a versão legível para referência):
Nó Code — Listar Diario
const { execSync } = require('child_process');
const NB     = '/home/USUARIO/bin/notebooklm';   // substitua USUARIO
const DIARIO = 'COLE_ID_DO_NOTEBOOK_DIARIO';     // mesmo ID do Salvar Diario

const listOut = execSync(`${NB} source list -n ${DIARIO} --json`,{encoding:'utf8',timeout:60000});
const data    = JSON.parse(listOut.slice(listOut.indexOf('{')));
const srcs    = data.sources || [];

const parts = [];
for(const s of srcs){
  let txt = '';
  try{
    const ft  = execSync(`${NB} source fulltext ${s.id} -n ${DIARIO}`,{encoding:'utf8',timeout:60000});
    const idx = ft.indexOf('Content:');
    txt = (idx>=0 ? ft.slice(idx+8) : ft).trim();
  }catch(e){ txt='(sem texto)'; }
  parts.push(`• [${(s.created_at||'').replace('T',' ')}]\n${txt}`);
}
return [{ json:{ diario: parts.length ? parts.join('\n\n---\n\n') : 'Diário vazio.' } }];

  2. Save + Active.

Workflow 4 — "Cerebro MCP" (servidor MCP — o ponto de entrada)

Este é o workflow central: ele recebe chamadas do Hermes via MCP e as distribui para os sub-workflows acima. Cada Call n8n Workflow Tool expõe uma ferramenta que o Hermes pode chamar por intenção.

  1. Crie: Cerebro MCP.
  2. Adicione o nó MCP Server Trigger. Configure:
    • Path: cerebro

  3. No conector de Tool do trigger (botão +), adicione uma Code Tool de diagnóstico:
    • Name: status_n8n
    • Description: Retorna a hora atual do servidor n8n. Use para testar se a conexão está funcionando.
    • Code (JS): return "n8n OK! Hora: " + new Date().toISOString();
  4. Adicione um segundo tool: Call n8n Workflow Tool para a consulta geral:
    • Source: Database → selecione Consulta Cerebro
    • Name: consulta_notebook_via_n8n
    • Description: Consulta um notebook do NotebookLM via n8n. Use SOMENTE quando o usuário pedir explicitamente "via n8n". Para perguntas normais, NÃO use — prefira a skill notebooklm.

  5. Adicione um terceiro tool: Call n8n Workflow Tool para salvar no diário:
    • Source: Database → Salvar Diario
    • Name: salvar_no_diario
    • Description: Salva uma anotação no diário pessoal. Use SEMPRE que o usuário pedir para anotar, guardar ou registrar algo no diário.
    • Campo texto: clique na varinha ✨.
  6. Adicione um quarto tool: Call n8n Workflow Tool para consultar o diário:
    • Source: Database → Consulta Cerebro
    • Name: consultar_diario

Fase III · Etapa 11

Automação: crons que alimentam e informam

Um cron é uma tarefa agendada — algo que roda sozinho em horários definidos (ex.: todo dia às 8h). É o que dá autonomia ao seu cérebro: em vez de você sempre pedir, ele se atualiza e te procura.

Aqui montamos dois exemplos: um briefing diário (ele pesquisa novidades e te manda um resumo no Telegram) e um pipeline que alimenta e limpa um notebook sozinho. A ideia é o cérebro trabalhar em segundo plano — inclusive enquanto você dorme.

Antes
  • Hermes como serviço (o scheduler roda junto).

Briefing diário com pesquisa web e entrega no Telegram:

bash
hermes cron create "0 8 * * *" "Pesquise na web as principais novidades do meu \
tema das ultimas 24h e entregue um briefing curto em PT-BR com 4-6 topicos, cada um \
com TITULO, contexto e o LINK real da fonte. Nao invente; descarte itens sem fonte." \
  --name briefing --deliver telegram

hermes cron run briefing && hermes cron tick   # testar na hora

"Cérebro que se alimenta e se limpa": feed (poucas URLs/dia) + rotação que, todo dia, remove fontes ruins (erro/404/bloqueadas) e poda as mais antigas:

bash
# feed 7h (NAO use --mode deep no diario!)
hermes cron create "0 7 * * *" "Pesquise 4-6 noticias do tema (URL real) e para cada \
uma rode: notebooklm source add <url> -n <ID_RADAR>. Reporte o que entrou." \
  --name feed --deliver telegram

# rotacao 7h30 (30min APOS o feed): SCRIPT deterministico que LIMPA + PODA
#   1) notebooklm source clean -y   -> remove erro/404/bloqueadas (ja assentadas)
#   2) poda as mais antigas se passar do cap (~200), usando caminho ABSOLUTO
hermes cron create "30 7 * * *" --name rotacao --script rotacao.py --no-agent --deliver telegram
⚠ Lições do pipeline

• source clean é a faxina (é interativo → use -y em script). NÃO o rode logo após adicionar (apaga fontes em processamento); rode ~30 min depois — é o que a rotação faz.
• Scripts --no-agent têm PATH mínimo → caminho absoluto do notebooklm (os.path.expanduser("~/bin/notebooklm")).
• Destrutivo = script determinístico, nunca o LLM decidindo.
• Exija 1 link real por item (o grátis alucina).

Fase III · Etapa 12

Roteamento por tema

Quando você tem vários notebooks, surge a pergunta: qual deles consultar para cada pergunta? O ideal é que você não precise dizer — o agente deve escolher pelo tema da pergunta (finanças → notebook de finanças; estudo → notebook de estudo). Isso é o "roteamento".

Aqui você ensina o Hermes a fazer isso sozinho (via SOUL.md) e descobre a lição mais importante sobre agentes: às vezes o modelo escolhe a ferramenta errada, e como o nome/descrição das ferramentas influencia mais essa escolha do que as instruções.

Antes
  • Vários notebooks + tools MCP.

O usuário não especifica notebook nem ferramenta — o agente decide. Acrescente ao final do SOUL.md (o bloco abaixo já anexa):

bash · anexa ao SOUL.md
cat >> ~/.hermes/SOUL.md <<'SOULEOF'

## Roteamento do cérebro
- Para perguntas de conhecimento, use a skill notebooklm DIRETA (acessa qualquer notebook).
- ESCOLHA o notebook cujo tema combina com a pergunta (use "notebooklm list").
- Nunca exija que o usuário diga o notebook nem a ferramenta.
SOULEOF
⚠ Lição central de agentes

No modelo grátis, o nome/descrição de uma tool pesa mais que a diretriz do SOUL. Se uma tool MCP "rouba" perguntas, renomeie/reescopa a descrição ("use SOMENTE quando o usuário disser 'via n8n'") para parar de competir com a skill direta.

Fase III · Etapa 13

Diário pessoal (memória append-only)

Até aqui o cérebro guarda fontes externas (artigos, vídeos). O diário guarda o que VOCÊ pensa: ideias, decisões, aprendizados — ditados por voz ou texto, no fluxo do dia. "Append-only" quer dizer que você só acrescenta entradas; depois consulta de forma semântica ("o que eu decidi sobre X?").

Esta etapa também traz uma lição prática forte: como forçar o agente a usar o cérebro certo quando uma ferramenta nativa dele (a memória interna) tenta "roubar" a tarefa — algo comum em modelos gratuitos.

Antes
  • n8n + MCP funcionando.

Um notebook (ex.: Bordo) onde você joga ideias por voz/texto e consulta depois.

⚠ O modelo "rouba" para a memória nativa

"Anota no diário" colide com a tool nativa memory; o grátis a prefere e ignora o SOUL. Duas frentes resolvem:

  1. Desligue a tool concorrente só no Telegram (tools são por plataforma): 
    bash
    hermes tools --summary
hermes tools disable --platform telegram memory
hermes gateway restart
  2. Crie tools dedicadas via n8n/MCP (o modelo segue uma tool de nome distinto melhor que uma instrução). Cada uma é uma sub-workflow + um Code que roda o notebooklm com caminho absoluto:
    • salvar_no_diario(texto) → source add --type text -n <BORDO>
    • consultar_diario(pergunta) → ask -n <BORDO> (síntese — "me lembre sobre X")
    • listar_diario() → source list + source fulltext (texto literal)
Como o diário rende mais

O ask sintetiza: ótimo p/ perguntas dirigidas, ruim p/ "liste tudo" (use listar_diario). Escreva com contexto ("decidi X porque Y").

Fase IV · Etapa 14

Liberar para múltiplos usuários

Por segurança, o Hermes só responde a IDs de usuário autorizados (por padrão, só o seu). Isso evita que qualquer pessoa que descubra seu bot ganhe acesso ao seu cérebro e às suas ferramentas. Esta etapa mostra como adicionar outras pessoas à lista de permissão — útil para compartilhar o assistente com família ou time.

Antes
  • Gateway do Telegram funcionando.

Por padrão o bot atende só os IDs autorizados. Passo a passo concreto:

  1. Cada pessoa pega o ID numérico dela mandando /start para @userinfobot no Telegram (ele responde com o ID).
  2. Descubra onde fica o .env: hermes config env-path (ex.: /home/USUARIO/.hermes/.env).
  3. Abra o arquivo no editor: nano ~/.hermes/.env
  4. Procure a linha TELEGRAM_ALLOWED_USERS. Se existir, acrescente os novos IDs (separados por vírgula); se não, adicione a linha no fim do arquivo: 
    ~/.hermes/.env
    TELEGRAM_ALLOWED_USERS=SEU_ID,ID_DA_PESSOA_2,ID_DA_PESSOA_3
  5. (Opcional) Para liberar um grupo inteiro, adicione também (o chat id de grupo começa com -100): 
    ~/.hermes/.env
    TELEGRAM_GROUP_ALLOWED_CHATS=-1001234567890
  6. Salve no nano: Ctrl+O → Enter → Ctrl+X.
  7. Aplique: hermes gateway restart. Peça para a pessoa mandar uma mensagem ao bot para testar.
⚠ Segurança

Quem você libera tem acesso total ao agente — cérebro, n8n e terminal. Libere só pessoas de confiança; para times, prefira TELEGRAM_GROUP_ALLOWED_CHATS num grupo controlado.

Acesso público (qualquer pessoa pode usar o bot)

Se você quer um bot aberto — sem lista de IDs, qualquer um que achar o bot pode conversar — basta remover ou deixar vazia a variável de allowlist. O Hermes passa a responder a todos.

  1. Abra o .env: nano ~/.hermes/.env
  2. Encontre a linha TELEGRAM_ALLOWED_USERS e apague-a completamente (ou deixe vazia: TELEGRAM_ALLOWED_USERS=). Se a linha não existir, o bot já está sem restrição por padrão.
  3. Salve: Ctrl+O → Enter → Ctrl+X.
  4. Aplique: hermes gateway restart.
🔴 Atenção máxima — acesso público significa acesso total

Sem allowlist, qualquer pessoa que descobrir o link do seu bot terá acesso a:

  • Todos os seus notebooks do NotebookLM (leitura e escrita de fontes).
  • O n8n e todos os workflows criados.
  • A tool terminal do Hermes — o que significa execução de comandos na sua máquina.

Use acesso público apenas se o seu Hermes está num ambiente isolado (ex.: VM na nuvem dedicada ao bot, sem dados sensíveis) e você entende os riscos. Para uso pessoal ou de time, a lista de IDs é sempre mais segura.

Fase IV · Etapa 15

Cloudflare Tunnel (acesso externo)

Seus serviços (como o n8n) rodam só na sua máquina, em localhost — invisíveis para a internet. Um túnel cria um endereço público e seguro (HTTPS) que aponta para um serviço local, sem você abrir portas no roteador. Serve para webhooks de entrada (um app externo aciona seu n8n) ou para acessar o n8n de qualquer lugar com uma URL amigável.

Existem dois modos: quick tunnel (URL descartável, bom pra testes) e named tunnel (URL fixa no seu domínio, permanente — o modo de produção). Esta etapa cobre os dois.

Antes
  • n8n ou outro serviço rodando em localhost.
  • Para o named tunnel: um domínio gerenciado na Cloudflare (DNS precisa estar na CF — plano gratuito basta).

Parte 1 — Instalar o cloudflared

bash
mkdir -p ~/bin
curl -L -o ~/bin/cloudflared \
  https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64
chmod +x ~/bin/cloudflared
cloudflared --version     # deve imprimir a versão
⚠ Oracle Cloud (ARM)

Se você está na VM Oracle (ARM), baixe o binário arm64: substitua cloudflared-linux-amd64 por cloudflared-linux-arm64.

Parte 2 — Quick tunnel (testes)

URL descartável, zero config, não precisa de domínio. Morre quando você encerra o processo.

bash
cloudflared tunnel --url http://localhost:5678
# imprime algo como: https://palavra-palavra-12345.trycloudflare.com
# abra essa URL no navegador — é o seu n8n acessível publicamente

Parte 3 — Named tunnel (produção)

URL fixa no seu domínio (ex.: https://n8n.seudominio.com), roda como serviço, permanece ativo após reboot. É o modo correto para uso real.

3.1 — Autenticar o cloudflared na sua conta Cloudflare

bash
cloudflared tunnel login
# abre o navegador — faça login na Cloudflare e selecione o domínio
# grava o certificado em: ~/.cloudflared/cert.pem

3.2 — Criar o túnel nomeado

bash
cloudflared tunnel create segundo-cerebro
# imprime algo como:
# Created tunnel segundo-cerebro with id abc123-def456-...
# Anote o ID — você vai usar a seguir.

3.3 — Criar o arquivo de configuração

bash · cria ~/.cloudflared/config.yml
cat > ~/.cloudflared/config.yml <<'EOF'
tunnel: abc123-def456-...          # substitua pelo ID do seu túnel
credentials-file: /home/USUARIO/.cloudflared/abc123-def456-....json

ingress:
  - hostname: n8n.seudominio.com   # substitua pelo seu subdomínio
    service: http://localhost:5678
  - service: http_status:404       # rota de fallback (obrigatória)
EOF

Substitua USUARIO, o ID do túnel e n8n.seudominio.com pelo subdomínio que você quer usar.

3.4 — Criar o registro DNS na Cloudflare

bash
cloudflared tunnel route dns segundo-cerebro n8n.seudominio.com
# cria automaticamente o registro CNAME no DNS da Cloudflare
# apontando n8n.seudominio.com para o seu túnel

3.5 — Testar antes de fixar como serviço

bash
cloudflared tunnel run segundo-cerebro
# deixe rodando e acesse https://n8n.seudominio.com no navegador
# se abrir o n8n com HTTPS: sucesso. Ctrl+C para parar.

3.6 — Instalar como serviço systemd (permanente)

bash
sudo cloudflared --config ~/.cloudflared/config.yml service install
sudo systemctl enable cloudflared
sudo systemctl start cloudflared
sudo systemctl status cloudflared   # deve estar: active (running)
💡 O túnel agora sobe no boot

A partir daqui, o túnel sobe automaticamente com a máquina. Para reiniciar: sudo systemctl restart cloudflared.

Parte 4 — Proteger o acesso com Cloudflare Access (autenticação)

Com o named tunnel, qualquer pessoa com a URL consegue ver o n8n. Para restringir com login (ex.: só quem tem o seu e-mail Google pode entrar), use o Cloudflare Access — gratuito para até 50 usuários.

  1. No painel da Cloudflare, acesse Zero Trust → Access → Applications → Add an application.
  2. Escolha Self-hosted.
  3. Em Application domain, insira seu subdomínio: n8n.seudominio.com.
  4. Em Policies, adicione uma regra: Allow → Emails → liste os e-mails autorizados (ou use Google Workspace, GitHub, etc.).
  5. Salve. Ao acessar o subdomínio, o Cloudflare vai exigir autenticação antes de chegar no n8n.
💡 Para webhooks (sem login)

Se um serviço externo precisar chamar o n8n via webhook (sem passar pelo login), crie uma política separada no Cloudflare Access do tipo Bypass para o caminho específico do webhook (ex.: /webhook/*). Assim o caminho do webhook fica aberto e o restante continua protegido.

Fase IV · Etapa 17

Por padrão, a Oracle bloqueia todo tráfego de entrada exceto SSH (porta 22). Para acessar o n8n pelo navegador, abra a porta 5678:

  1. No Console, acesse Networking → Virtual Cloud Networks → (sua VCN) → Security Lists → Default Security List.
  2. Clique em Add Ingress Rules e preencha:

    • IP Protocol: TCP
    • Destination Port Range: 5678

sudo iptables -I INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
# para persistir após reboot:
sudo apt install iptables-persistent -y && sudo netfilter-persistent save

Parte 5 — Instalar o ecossistema (mesmas etapas do guia)

Na VM, siga exatamente as mesmas etapas que você já fez no WSL2:

  1. Etapa 01: verifique Python/Node (sudo apt update && sudo apt install python3 python3-pip nodejs npm git -y).
  2. Etapa 03: instale o Hermes (pip install hermes-agent && hermes postinstall).
  3. Etapa 04: instale o NotebookLM CLI (venv + playwright).
  4. Etapa 05: crie o SOUL.md.
  5. Etapa 06: configure o gateway do Telegram (hermes gateway setup).
  6. Etapa 08: instale como serviço systemd (hermes gateway install).
  7. Etapas 09–13: instale o n8n, crie os workflows e conecte o MCP.
💡 Sem linger necessário

Na Oracle Cloud você não precisa do loginctl enable-linger — o usuário ubuntu já tem sessão persistente no systemd (diferente do WSL2, onde o subsistema Linux pode ser desligado). Os serviços simplesmente ficam ligados enquanto a VM estiver rodando.

Parte 6 — O detalhe mais importante: login do NotebookLM

O notebooklm login abre um navegador Chromium para fazer o login no Google — algo impossível numa VM sem interface gráfica. A solução é fazer o login na sua máquina local e copiar a sessão para a VM:

  1. Na sua máquina local (WSL2), faça o login normalmente: notebooklm login.
  2. Localize o arquivo de sessão gerado: 
    bash — na sua máquina LOCAL
    ls ~/.notebooklm/profiles/default/storage_state.json
  3. Copie o arquivo para a VM via scp: 
    bash — na sua máquina LOCAL
    # crie o diretório na VM primeiro:
ssh -i ~/Downloads/ssh-key-XXXX.key ubuntu@IP_DA_VM \
  "mkdir -p ~/.notebooklm/profiles/default"

# copie o arquivo de sessão:
scp -i ~/Downloads/ssh-key-XXXX.key \
  ~/.notebooklm/profiles/default/storage_state.json \
  ubuntu@IP_DA_VM:~/.notebooklm/profiles/default/storage_state.json
  4. Na VM, confirme que funcionou: notebooklm auth check (deve mostrar ✓).
⚠ A sessão expira periodicamente

O Google invalida a sessão do NotebookLM de tempos em tempos (dias a semanas). Quando o notebooklm auth check falhar, repita o processo: login local + scp do storage_state.json para a VM. Não há como automatizar completamente essa etapa, pois o Google exige autenticação interativa.

Parte 7 — Acessar o n8n pelo navegador

Com a VM rodando e a porta 5678 aberta, acesse o n8n de qualquer lugar:

browser
http://IP_PUBLICO_DA_VM:5678

Para uma URL mais amigável e com HTTPS (ex.: https://n8n.seudominio.com), use o Cloudflare Tunnel com named tunnel (Etapa 15 deste guia). É grátis e leva ~10 minutos.

Parte 8 — Verificar que tudo sobe no boot

bash — na VM Oracle
systemctl --user status hermes-gateway    # deve estar active (running)
systemctl --user status n8n               # deve estar active (running)
hermes mcp test n8n                       # deve descobrir as tools
notebooklm list                           # deve listar seus notebooks

Para simular um reboot e confirmar que tudo volta: sudo reboot → aguarde ~1 minuto → reconecte via SSH e rode os comandos acima.
